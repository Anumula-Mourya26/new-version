ANNSETU"Bridge to the Grain"Engineering Blueprint — Live Gate & Queue Transparency Layer for MSP ProcurementSIH26032 · Ministry of Consumer Affairs, Food & Public DistributionTrack: Software · Theme: Smart AutomationPrepared as a Principal-Engineer build specification — not generic hackathon advice.1. ProductProject name: AnnSetu (from Hindi anna — grain/food, + setu — bridge): "Bridge to the Grain"Tagline: From "your slot is Tuesday" to "your money is in your account" — live, honest, farmer-facing MSP procurement.ProblemFarmers selling foodgrain at MSP procurement centres face three compounding failures: (1) they physically wait for hours because everyone assigned to the same day arrives at the same time, since existing slot systems are date-level, not time/position-level; (2) they get no live signal once they leave home, so a delay, backlog, or centre overload is discovered only on arrival; and (3) once their produce is sold, they often cannot tell whether payment has actually reached them, especially in commission-agent (arhatiya) mediated states where the money passes through an intermediary before it reaches the farmer's account.SolutionAnnSetu is a live operations layer that sits beside existing state procurement portals (MP e-Uparjan, Punjab e-Kharid/e-PMB, RAJFED, etc.) rather than replacing them. It adds exactly the three things verifiably missing from every system studied: a gate-fed live queue position and ETA (computed with queueing-theory math, not machine learning), a staged payment-trust timeline that explicitly tracks the agency → intermediary → farmer leg, and a district command view that turns "this centre is overloaded" from a passive chart into a one-click redirect action for officers.UsersFarmer (primary) — registers, books a slot, checks live queue position/ETA before and during travel, tracks payment status.Centre operator — manages gate check-in, sees live load against capacity, triggers delay notices.District food & civil supplies officer — sees multi-centre load, approves/triggers redirect suggestions, views district analytics.Commission agent / arhatiya (secondary, mandi states) — bulk view of their client farmers' slots and payment stage.System/AI — the queue engine, notification engine and (post-MVP) rebalancing heuristics acting autonomously on live data.MVPFarmer registration (simulated Aadhaar/land/bank fields) + crop and quantity declaration.Slot booking against a centre with a defined daily capacity.Gate check-in (QR/token scan) generating a live arrival timestamp.Live queue position + ETA from a deterministic M/M/c-style queueing calculation.SMS/app notifications at three transitions: slot confirmed, turn approaching, payment status change.Status timeline: registered → slot booked → arrived → quality-checked → weighed → payment advice → credited.Single centre-operator dashboard.Future scopeDistrict-wide multi-centre dashboard with one-click redirect suggestions (built in MVP as a stretch goal, hardened post-hackathon).Real integration with a state procurement portal's registration/slot data and with PFMS as the payment source of truth.Bilingual/multilingual UI (Hindi + one regional language for demo, extensible architecture).WhatsApp/IVR channels alongside SMS.Lightweight arrival-rate smoothing (regression/heuristic) as an "advanced" add-on — not the centrepiece.True multi-season demand forecasting once real historical data is available via a government partnership.2. Complete User WorkflowEach actor's flow is shown as Input → Processing → Decision → Output. All four flows share the same underlying database and queue engine.A. FarmerINPUT  Aadhaar-linked mobile no. + OTP · land record ref · bank/PFMS ref · crop, variety, estimated quantity        │PROCESSING  Registration validated (duplicate check, sharecropper consent flag) → farmer sees centres with live  load → selects centre + date window → system offers earliest low-congestion slot        │DECISION  Accept suggested slot?  YES → slot booked, token issued, SMS/app confirmation with unique code                          NO  → pick alternate centre/time, re-run suggestion        │OUTPUT  Confirmed slot + token · pre-departure live queue snapshot ("Centre load: Medium, ETA today ~40 min")  · at gate: QR check-in → live position/ETA screen · post-sale: status timeline + payment-stage SMSB. Procurement Centre (Operator)INPUT  Daily capacity (weighing points × shift hours) · gate check-in events · quality/weighing results        │PROCESSING  Queue engine recomputes position/ETA for every waiting farmer on each new check-in or completed  service · dashboard shows arrivals-vs-capacity curve for the day        │DECISION  Load nearing capacity?  YES → operator issues delay notice / requests district redirect                          NO  → normal FIFO-with-priority processing continues        │OUTPUT  Called token → quality/weighing entry → procurement record + digital receipt · updated live queue  broadcast to all waiting farmers' apps/SMSC. Government / District AdminINPUT  Aggregated live load from all centres in district · historical tonnage/capacity figures        │PROCESSING  Command dashboard colours centres green/amber/red by live queue length vs. capacity · flags  outlier centres and payment-delay clusters        │DECISION  Centre in red?  YES → approve/trigger "redirect next N unbooked registrants to nearby centre"                  NO  → monitor; review season-level analytics and forecasts        │OUTPUT  Redirect action applied to slot-suggestion engine · district/season reports · escalation alerts to  state department for outlier centres or payment-adoption gapsD. System / AI (Queue & Notification Engine)INPUT  Gate arrival timestamps · per-centre service-rate history · booking calendar · payment-stage events        │PROCESSING  M/M/c-style ETA calculation per centre, recomputed on each event · notification triggers evaluated  against thresholds (position <= 5, status change, etc.)        │DECISION  Threshold crossed?  YES → enqueue notification job (SMS/push) · load > 90% capacity? → flag for                            redirect suggestion                      NO  → update live state only, no notification        │OUTPUT  Live queue_state records · notification_log entries · redirect_suggestion records for officer review3. Technology SelectionEvery choice below is made against the actual constraints found in the research: seasonal load spikes, low-end phones, intermittent connectivity, a relational domain model, and a queueing problem that is solvable with statistics, not deep learning. Nothing here is chosen because it is popular.LayerChosen technologyAlternative consideredWhy chosenFrontend (farmer + dashboards)React 18 + Vite, deployed as a PWAPlain HTML/JS; Next.js; Flutter webTeam already needs SSR-free, fast iteration; PWA gives offline caching and installability without an app-store review cycle — matches Part 18's PWA recommendation for low-end phones.Mobile channelPWA first; native Android only if a judge/pilot partner requires itReact Native full appResearch found no evidence smartphone-only design is safe (low-end phones, intermittent data) — a PWA plus SMS/IVR fallback covers more real farmers than a native app would, for far less build cost.BackendPython + FastAPINode.js + ExpressThe queue engine is fundamentally a numeric/queueing-theory computation; FastAPI keeps that logic and any later ML/forecasting work in one language, with async support for WebSocket-heavy live updates and auto-generated OpenAPI docs for the API contract in Section 6.Real-time channelWebSockets (FastAPI native) for live queue positionPolling; SSEPosition/ETA must update sub-second on the farmer's screen without hammering the API; WebSockets are the standard fit and FastAPI supports them natively.DatabasePostgreSQLMongoDBThe domain is heavily relational (farmers↔slots↔tokens↔payments, foreign keys, referential integrity for audit trails that a government system will be judged on) — this is a textbook relational schema, not a document store problem.Cache / live state / queueRedisIn-memory Python dict; RabbitMQLive queue_state must be read with very low latency by many concurrent farmer clients, and notification dispatch is naturally a job queue; Redis does both with one dependency, which matters for a student-team deployment footprint.AI / queueing & forecastingPython (NumPy/SciPy for M/M/c math; scikit-learn only for the optional heuristic add-on)Deep learning frameworks (PyTorch/TF)Section 8 shows the core ETA calculation is closed-form queueing theory, not ML — pulling in a deep-learning stack would be technology chosen for buzzwords, not need, exactly what Part 16 of the research warns against.NotificationsSMS via a standard gateway API (e.g. Twilio/MSG91-class provider) as baseline; app push as secondary; WhatsApp/IVR as future channelsPush-only; WhatsApp-onlySMS is documented as the channel every existing state system already relies on for farmers without smartphones (Part 18) — it must be the baseline, not an afterthought.Deployment (prototype)Single cloud VM or free-tier PaaS (e.g. Render/Railway) for backend + managed Postgres + Redis add-on; static hosting (Vercel/Netlify) for frontendKubernetes clusterA 36-hour to few-week student build does not need container orchestration; a simple, restartable deployment that a judge can open in a browser is the right scope, with a documented path to containerization for the pilot stage (Section 18).AuthOTP (mobile) for farmers; email/password + role claims (JWT) for operator/district/adminAadhaar e-KYC live integrationNo public Aadhaar e-KYC sandbox is available to a student team; OTP-based mobile auth mirrors how real state portals already authenticate farmers, with Aadhaar/land-record integration flagged explicitly as a future, government-partnership step.5. Queue EngineThis is the product's centrepiece and its most defensible technical claim: a deterministic, explainable queueing-theory model, not a black-box prediction. It is deliberately not machine learning — see Section 8 for why.Token generationOn gate check-in, the Slot & Token Service verifies the scanned QR/booking code against the day's booking, then issues a token with a per-centre, per-day sequential token_number and records issued_at as the live arrival timestamp. This timestamp is the single most important new data point the whole system introduces — no existing system studied exposes it back to the farmer.Queue orderingBase ordering is FIFO by issued_at within a centre. On top of FIFO, a bounded priority adjustment is applied (see Priority below) so the visible order is FIFO-with-priority, not pure priority-jumping, to preserve fairness and match the fairness expectation already documented for existing token systems.PriorityBooked-slot arrivals within their window get standard FIFO priority.Walk-ins (where a centre's policy allows them) are inserted after all currently-booked, on-time arrivals for that window — never ahead of a farmer who followed the process.A small, capped priority boost (configurable per centre, default 0) is available for documented special cases (e.g. elderly/disabled farmers) — off by default in the MVP to avoid opaque queue-jumping perceptions.Processing rate (service rate, µ)Computed per centre from weighing_points × an empirically observed average service time per farmer (seeded from simulated/calibrated data for the demo; replaced with a rolling average of actual procurement.recorded_at − token.issued_at deltas once real data exists).ETA calculationModelled as an M/M/c queue per centre: c = weighing_points (servers), λ = live arrival rate from the last N check-ins, µ = average service rate per server. For a farmer at position p in the live queue, ETA ≈ p / (c·µ), recomputed on every check-in and every completed procurement so it stays live rather than a one-time estimate. This is the "straightforward operations-research calculation, not deep ML" the research explicitly identifies as the highest-value, most feasible feature.No-showA booking whose slot window closes without a check-in is marked no_show; its capacity_units are released back to the slot (visible to the redirect/rebalancing logic) and logged for the no-show-rate metric in Section 16, which is honestly flagged as unverified against any public baseline and treated as a hypothesis to validate against pilot data.CancellationA farmer or operator can cancel a booking before check-in; capacity is released immediately and, if the slot had been full, a notification offer can go to a waitlisted farmer (future scope, not MVP).ReschedulingImplemented as cancel + rebook against a new slot in one transaction, so booked_units accounting never double-counts; the farmer keeps the same unique_booking_code lineage for support traceability.Centre capacitydaily_capacity_units on centres and capacity_units per slot are the two capacity inputs; the Slot & Token Service enforces them with a row-level lock on slots.booked_units at booking time to prevent overbooking races.Real-time updatesEvery check-in or completed procurement event recomputes queue_state for all waiting tokens at that centre and pushes the delta over the centre's WebSocket channel; Redis holds the authoritative live snapshot for sub-second reads, with PostgreSQL as the durable, queryable history for analytics and disputes.8. Farmer ExperienceDesigned against documented on-ground realities (Part 18 of the research): token-date confusion, centralised single-point issuance failures, and low PFMS adoption by intermediaries mean the design cannot assume a smartphone or constant connectivity.Low literacyIcon-led UI with minimal text; status timeline uses colour + icon states, not paragraphs.Voice/IVR status lookup as a future channel for farmers who cannot easily read SMS.CSC/kiosk-assisted registration flow, mirroring how e-Uparjan-style portals already lean on Common Service Centres.Regional languagesHindi + one additional regional language (e.g. Punjabi or Telugu depending on the pilot state) for the demo, with all UI strings and SMS templates externalised so more languages are a translation-file addition, not a code change.Low bandwidth / low-end phones / intermittent internetPWA architecture: caches the last known queue state client-side and syncs on reconnect rather than showing a blank/broken screen.SMS is never a fallback-only channel — it is designed as a first-class channel from day one, since it is the one channel guaranteed to work on any phone.Payload sizes kept minimal; images/maps are optional enhancements, never required for core flows (booking, check-in, status).Channel decision: PWA vs Android vs SMS vs IVRPWA is used instead of a native Android app because it avoids app-store distribution friction for a government pilot and still gives installability and offline caching. SMS is mandatory as the universal baseline, matching every existing state system studied. IVR is placed in future scope, not MVP, because a fixed-menu IVR tree is buildable quickly but adds limited unique value over SMS for the specific events in Section 9 — it becomes valuable later mainly for two-way status lookup by farmers without any digital literacy at all.11. TestingUnit tests — every service function (registration, slot/token, queue engine's ETA formula, payment stage transitions) tested in isolation with pytest, including edge cases (zero arrivals, single-server centre, first booking of the day).Integration tests — service-to-DB flows: booking under a row-level lock, check-in creating a token and queue_state row, procurement auto-creating a payment record.API tests — every endpoint in Section 6 tested for the happy path and each listed error code, using FastAPI's TestClient.Load tests — simulate concurrent bookings against a single slot to confirm no overbooking; simulate a burst of gate check-ins to confirm queue_state recomputation stays correct and fast under load (target: sub-second propagation to WebSocket clients at 50+ concurrent tokens).AI tests — for the ETA formula specifically: compare predicted vs. actual wait on seeded historical data and assert mean absolute error stays under a defined threshold; regression-test the formula against known M/M/c textbook cases.Security tests — RBAC matrix (every route × every role), OTP rate-limiting, input validation/injection checks, verification that Aadhaar/bank fields are stored as tokenised references, not raw values.User tests — a small moderated walkthrough of the farmer app with 2–3 non-technical testers (ideally including a low-literacy or regional-language speaker) to sanity-check the icon-led, low-literacy design from Section 10.18.
